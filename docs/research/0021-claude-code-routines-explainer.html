The Night Janitors: how the Claude Code team lets Claude clean up after itself

About a 9-minute read. Written for anyone who has ever opened an old project folder and quietly closed it again.

Every big software project has a junk drawer. Code nobody calls any more. Tests that pass no matter what. A switch that was supposed to be flipped "for a week" in 2024. Nobody cleans it because nobody gets promoted for cleaning it. This is the story of a team that hired a robot to do the cleaning, every single day, and what happened when they counted the results.

First, the mess

Picture a busy restaurant kitchen. During service everyone is cooking. Plates go out, orders come in, and a sauce pan gets shoved to the back of the stove "for later". Nobody has time to scrub it. By midnight the kitchen is a disaster, and yet tomorrow's service starts at 11.

Software is exactly like that, except the pans never smell. A codebase is the full set of files a product is built from. Claude Code, the programming assistant made by Anthropic, is built from six of them: an iPhone app, an Android app, a desktop app, a web app, the command-line tool, and a toolkit for other developers. Each one is a kitchen. Each one accumulates pans.

Six kitchens, six piles of pans. Each pile is a kind of mess that builds up when everyone is busy shipping.

Here's the thing about these pans. None of them stop the restaurant from serving food. Dead code doesn't crash anything. A useless test still shows green. So the mess is invisible to customers and boring to engineers. That is the worst possible combination. It means it never gets done.

Then, a weird experiment

Boris Cherny is the engineer at Anthropic who created Claude Code. In mid-2026 he tried something he himself called "a weird experiment": what if Claude simply took over the day-to-day maintenance of the apps?

The setup is almost comically simple. There is a Slack channel. (Slack is the office chat tool most tech companies live in.) The channel is called proj-claude-maintains-apps. In it, Claude is given a short, plain-English job description for each kind of cleaning. Not a 40-page prompt. Something closer to a note you'd leave for a new hire: "every day, open the iPhone app in the simulator, tap around until it crashes, and send me a fix."

The whole "architecture": a Slack channel, a few plain-English notes, and Claude reporting back. The hard part was never the plumbing.

Each of these standing instructions is what Claude Code calls a routine. Think of a routine as a saved to-do that runs itself: a job description, the folder of code it is allowed to touch, and a trigger that says when to go. The trigger can be a clock ("every night"), a message from another system ("when the error monitor shouts"), or an event in the code repository ("when someone opens a pull request"). It runs on Anthropic's servers, so it keeps going when your laptop is shut. Anthropic has since started calling them "scheduled tasks" in the documentation, but the team still says routines.

So what

The routines are not a new product feature the team invented for themselves. Anyone with a Claude Pro, Max, Team or Enterprise plan can create one with the /schedule command. What's notable is that the people who built the tool are now eating their own cooking, and publishing the numbers.

Meet the twelve janitors

Cherny's team runs about a dozen routines a day. Eleven have names that leaked into the press coverage. Each one has one job, like a specialist on a cleaning crew. Here they are, with what the jargon actually means.

The headline act

Dead Code Removal

Dead code is code that nothing ever calls any more. It costs nothing to run but everything to read: every new engineer wastes time wondering what it does. This janitor deletes code it can prove is unreachable. For code it merely suspects, it does something clever that we'll come back to.

The coin-flipper catcher

Flaky-Test Fixer

A test is a tiny program that checks the real program still works. CI (continuous integration) is the robot that runs every test on every change. A flaky test passes on Monday and fails on Tuesday with no change in between, usually because of timing or shared state. Teams learn to ignore it, and then it hides a real failure. This janitor finds the root cause and fixes it.

The fake-guard remover

Useless Test Pruner

Some tests cannot fail. They check that a function was called, or that one equals one. They give a warm green glow and protect nothing. This janitor deletes them, so the remaining green actually means something.

The switch puller

Shipped-Feature Inliner

A feature flag is an on/off switch in the code that lets a team release a feature to 1% of users, then 10%, then everyone. Once it's at 100% the switch is pure clutter, and every switch doubles the number of paths to test. This janitor removes switches that have been fully on for ages and keeps only the "on" path.

The attic clearer

Ant-only Shipper

"Ant" is Anthropic slang for an employee. Engineers build little features just for themselves, then forget them. This janitor looks at whether anyone actually uses each internal-only feature, and either ships it to everyone or deletes it. No more attic.

The twin merger

Dup Unifier

Two engineers, two years apart, write nearly the same helper. Now a bug fix in one misses the other. This janitor finds near-duplicates, including ones that drifted slightly apart, and merges them into one.

The untangler

Logic Simplifier

Business rules pile up as "if this, then unless that, except when". This janitor flattens nested conditions into something a human can read in one pass.

The detective

Logic Bug Fixer

Some bugs don't crash anything; they quietly give the wrong answer. This janitor builds a model of what the complicated logic is supposed to do, compares it with what it actually does, and fixes the gap.

The de-architect

Abstraction Improver

An abstraction is a layer that hides detail: a "Payment" class so you don't think about card networks. Useful until someone builds a layer on a layer on a layer for a thing used once. This janitor collapses over-engineered towers back to what the code needs.

The traffic cop

Abstraction Police

Well-built software is layered: the screen talks to the logic, the logic talks to the database. A layer violation is a shortcut where the screen reaches straight into the database. It works today and breaks everything later. This janitor finds the shortcuts and reroutes them.

The toddler

Crash Fuzzer

Fuzzing means feeding a program random input to see what breaks. This janitor opens the real app in a simulator, no fake components, and taps around like a toddler with a phone until it crashes. Then it traces the crash back to its cause and writes the fix.

The mystery

Routine number twelve

Cherny said twelve. The reporting lists eleven. Possibly a docs updater, possibly a dependency bumper, both of which appear in Anthropic's own routine examples. We don't know, and this page won't guess.

The cleverest trick: log first, delete tomorrow

Back to the dead-code janitor, because it contains the single best idea in the whole experiment.

Deleting dead code is scary. "Nothing calls this" is easy to say and hard to prove: code can be reached through a text string, a dynamic import, a scheduled job you forgot about. Humans deal with the fear by not deleting anything. Ever.

Claude's routine deals with it differently. If it can prove code is unreachable, it deletes it. If it only suspects, it adds a single line of logging that shouts "I ran!" and walks away. The next day, it checks the logs. Silence? Now it has evidence, not a hunch, and the code goes.

Guessing becomes measuring. The routine turns "I think this is dead" into "nobody touched it for a day, here is the log to prove it".

So what

This is a general pattern, not a coding one. Before you remove anything you're unsure about, a report, a meeting, a data feed, instrument it for a cycle and let the silence make the case. It turns a judgment call into a data point.

The scoreboard

Here is where it stops being a cute story. Every routine ends by opening a pull request, or PR: a proposed change parked for review, never a direct edit to the live code. Each PR then goes through two gates: Claude Code's own automated review, then a human. Over the first few weeks the numbers looked like this.

388pull requests opened by the routines
180merged into the real code after both reviews
208closed without merging
46%merge rate

The funnel. Note that nothing skips the human gate, which is both the safety net and, as we'll see, the bottleneck.

Is 46% good or bad?

Depends what you compare it to. If a junior engineer had 54% of their PRs thrown out, you'd have a word with them. But a junior engineer costs a salary and gets demoralised. A routine costs some compute and tries again tomorrow. The right comparison isn't "how many PRs were rejected", it's "how much cleaning got done that otherwise would have been zero". On that measure, 180 merged cleanups in a few weeks across six codebases is a number no human team would have produced, because no human team would have been asked to.

What happens to the 208?

This is the second clever bit. When a PR misses, the team does not fix the code by hand. They edit the routine's instructions so that tomorrow's attempt is better. Cherny says this tuning can take a few days per routine. In other words, the team is training a cleaner, not doing the cleaning. Every rejection is a note in the job description, and the job description compounds.

The feedback loop. Rejections improve the instructions, so the same routine gets sharper every day without anyone touching code.

The quieter routines on laptops

The Slack-channel janitors are the headline, but Anthropic's own tips page shows a second tier the Claude Code team runs locally, with a command called /loop that repeats a task every few minutes for up to three days. These aren't cleaners so much as a very patient assistant.

The documentation also lists the "starter" routines Anthropic suggests to everyone: nightly labelling of new issues, a draft fix when the error monitor fires, a checklist review when a PR opens, smoke checks after each deploy, and a weekly sweep for docs that mention changed functions.

Why this works, in three lines

1. One job per janitor. "Clean the kitchen" fails. "Remove feature flags that have been fully on for 90 days" succeeds. Narrow, checkable, boring.

2. Always a draft, never a commit. Every routine ends in a PR a human can reject in two seconds. The safety net is what makes the autonomy affordable.

3. Tune the note, not the output. Fixing the code by hand teaches nothing. Editing the instruction compounds.

What this means for Alpha Signal

We already run a version of this. Plan 0019 gave the project an agent org: a CEO (Amit), a CIO, a CTO and about a dozen seats, each owning a kind of recurring task that runs on the morning cron and files a memo. That is a routine with a job title.

Three things from the janitor story are worth stealing:

  • The log-first delete. Our codebase has tools, tables and factors that may be dead (the factor_library bench, old study tools, retired run.sh cases). A seat that instruments a suspect for a week via run_events, then proposes the deletion as a PR with the silent log attached, fits the existing "silent failures are the enemy" rule exactly.
  • The useless-test pruner. We have a rule that every health check must be able to fail (ADR 0060). The same bar applied to tests/ would be a one-line routine.
  • Measure the merge rate. The org already grades memos. Counting proposals merged versus rejected per seat, the way Cherny counts PRs, is the honest scorecard for whether a seat earns its tokens.
So what

None of this requires new infrastructure. It requires writing three or four plain-English notes, each ending in "open a PR, never commit", and reading the rejections as instructions to edit the note.

Jargon buster

Codebase
All the source files a product is built from. Claude Code has six.
Routine / scheduled task
A saved Claude Code job: a prompt, the repositories it may touch, and a trigger (schedule, API call or GitHub event). Runs on Anthropic's servers.
Pull request (PR)
A proposed change to the code, parked for review. "Merged" means accepted into the real code; "closed" means rejected.
Merge rate
Merged PRs divided by PRs opened. Here 180 / 388 = 46%.
CI
Continuous integration: the robot that runs every automated test on every proposed change.
Flaky test
A test that passes and fails on the same code depending on timing or luck.
Dead code
Code that nothing calls any more. Harmless to run, expensive to read.
Feature flag
An on/off switch in the code used to release a feature gradually. Clutter once it's fully on.
Abstraction
A layer that hides detail behind a simpler name. Good in moderation.
Layer violation
A shortcut between layers that should not talk directly, e.g. the screen reading the database.
Fuzzing
Feeding random input or random taps to a program to make it crash on purpose.
Slack / Claude Tag
Slack is a workplace chat tool. Claude Tag is Claude running inside Slack, which is where these routines are driven from.
Ant
Anthropic slang for an Anthropic employee. "Ant-only" means internal-only.

Tail piece

There's an old joke that the most dangerous phrase in engineering is "I'll clean that up later". Later never has a date. What Cherny's experiment really did was give later a date: tomorrow, 2 a.m., every day, with a note to a robot that doesn't find the work boring. The code didn't get smarter. The calendar did.
